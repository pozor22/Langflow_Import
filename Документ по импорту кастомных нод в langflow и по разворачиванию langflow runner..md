### 1. Импорт кастомных нод в LangFlow.

В данном блоке мы разберем как можно реализовать импорт кастомных нод на серверный LF, для этого все будет показано на демонстравном примере. Примечание, данный импорт нод происходит через файлы `.py`.

Данный проект так же будет опубликован на гитхабе - .

Начнем с того, что нужно развернуть LF, для этого мы используем Docker и Docker-Compose, создаем DockerFile, который будет скачивать последний образ LF и запускать его, так же туда я добавил команду для установки всех зависимостей из `requirements.txt`, пример кода файла:

Пример кода DockerFile для поднятия LF.
```DockerFile
FROM langflowai/langflow:latest  
  
COPY requirements.txt /tmp/requirements.txt  
  
RUN uv pip install -r /tmp/requirements.txt  
  
CMD ["langflow", "run", "--env-file", "/app/.env", "--host", "0.0.0.0", "--port", "7860"]
```

Это стандартный DockerFile для LF, дополнительные параметры для импорта наших нод, нужно будет проставить в Docker-Compose, но для начала добавим папку, из которой будут импортироваться ноды, еще можно создать на любом уровне проекта, так как дальше мы еще будем монтировать в LF, в данном примере создана папка `custom_components` на уровне с DockerFile и Docker-Compose и все следующие действия будут расписаны для получившийся структуре, итоговая структура получается такой, представлено на рисунке 1.

Далее перейдем к docker-compose файлу.

Пример кода для docker-compose для поднятия обычного LF и бд для него.
```docker-compose.yml
services:  
  langflow:  
    build:  
      context: .  
      dockerfile: Dockerfile-langflow  
    container_name: langflow  
    pull_policy: always  
    user: "0:0"  
    ports:  
      - "7860:7860"  
    depends_on:  
      - postgres  
    environment:  
      - LANGFLOW_DATABASE_URL=postgresql://langflow:langflow@postgres:5432/langflow  
      - LANGFLOW_CONFIG_DIR=/app/langflow  
      - LANGFLOW_COMPONENTS_PATH=/app/custom_components  
    volumes:  
      - langflow-data:/app/langflow  
      - ./custom_components:/app/custom_components  
  
  postgres:  
    image: postgres:16  
    container_name: lf_postgres  
    environment:  
      POSTGRES_USER: langflow  
      POSTGRES_PASSWORD: langflow  
      POSTGRES_DB: langflow  
    ports:  
      - "5432:5432"  
    volumes:  
      - pgdata:/var/lib/postgresql/data  
  
volumes:  
  pgdata:  
  langflow-data:
```

Это стандартный пример такого файла для простого локального запуска LF, нас интересуют один параметр `LANGFLOW_COMPONENTS_PATH` в него нам нужно указать путь, где в контейнере будет храниться наша папка с нодами. А для того чтобы импортировать сразу из проекта ноды, нам нужно вмонтировать нашу папку в docker, для этого прописываем нашу папку в проекте и куда мы монтируем данные в контейнере, пример:

Монтировка нашей папки с нодами в контейнер.
```docker-compose.yml
volumes:  
      - ./custom_components:/app/custom_components 
```

После этого все ноды буду импортированы в проект и можно будет их использовать в любых пайплайнах.

P.S. Конечно все эти параметры для `environment` нужно хранить в .env, просто это демо проект.

##### 1.5. Дополнительная информаци:
- **Важно:** если нода по каким-то причинам вызывает ошибку, например, синтаксическая или вы не установили нужные пакеты, то она не будет отображаться в UI LF.

- Импортировать можно любого класса ноды.
- При обновлении ноды из папки, все поставленные ноды просят либо подтвердить обновление, либо отказаться от него, пример на рисунке 8. LF проверяет, обновилась ли нода, только после перезапуска контейнера, поэтому если во время работы LF вы измените в папке код ноды, то это все подтянется только после перезапуска контейнера.

### 2. Langflow runner.

Следующий блок будет посвящен Langflow runner. Идея такая, langflow имеет фронт часть приложения, где мы можем создавать наши пайплайны, ноды и т.д. а так же можем и запускать наши пайплайны и можем к ним обращаться через `requests` на Python например. Но если мы хотим локально через UI создавать пайплайны, а на прод просто их импортировать и чтобы они просто там запускались без интерфейса, то для этого нам нужен LF runner, на самом деле это тот же самый LF, только будем его запускать без фронт, только бек.

Для чего это нужно, во-первых, не получиться зайти в пайплайн и что-то изменить, только если через утилиту nano найти .json файл с пайплайнов и что-то сделать, но там все равно ничего понятно), во-вторых, к таким пайплайнам можно обратиться только через api ключ, не получиться получить учетные данные и войти через UI и что-то сделать с пайплайном, в третьих, в LF есть проблема с совместной разработкой, если два человека будут одновременно работать на одном пайплайне например на деве, то что-то может не сохраниться и сломаться, поэтому лучше на прод отправлять уже полностью готовые пайплайны, чтобы ничего не слетело, в четвертых, фронт все равно будет потреблять ресурсы сервера, а на проде такое недопустимо.

Далее разберем как поднять в контейнере бек LF и сделать так, чтобы мы могли спокойно импортировать наши готовые пайплайны. DockerFile нам менять не требуется, но если мы работаем только с ним, то нужно добавить параметр `--backend-only` в команде запуска.

Пример Dockerfile для запуска только бекэнда LF.
```DockerFile
FROM langflowai/langflow:latest  
  
COPY requirements.txt /tmp/requirements.txt  
  
RUN uv pip install -r /tmp/requirements.txt  
  
CMD ["langflow", "run", "--backend-only", "--env-file", "/app/.env", "--host", "0.0.0.0", "--port", "8082"]
```

Если мы работаем с docker-compose, сделать так же или в `environment` добавить одно поле, `LANGFLOW_BACKEND_ONLY=true`, после этого будет запускаться только бек, пример:

Пример Docker-Compose для запуска только бекэнда LF.
```Docker-Compose.yml
environment: 
  - LANGFLOW_BACKEND_ONLY=true
```

После этого можете зайти на ваш url и по пути /, вы должны получить это

Ответ запущенного только бек части LF.
```json
{
  "detail": "Not Found"
}
```

Вы можете зайти на `/docs` для просмотра апишек через swagger, для нас там будет важен путь POST /api/v1/api_key/, где мы и сможем сгенерировать наш API ключ для работы с сервером.

P.S.В моем примере на гит-хабе я поднимаю для LF, с фронтом и без, поэтому разные порты. Так же еще информация для локальной разработки, если вы сначала запустите только бек, а потом по какой-то причине решите этот же контейнер запустить с фронтом, а потом снова поднять только бек, то если вы перейдете по нашему пути, то вы увидите фронт часть и причем рабочую, как я понял, это происходит из-за кеша вашего браузера и если перейти в другой браузер, а лучше всего еще и перед этим почистить все образы и тома от контейнеров, то будет открываться только бек.

Далее поговорим про импорт наших пайплайнов, есть два способа:

##### 2.1. Импорт через встроенную папку.
Для начала нужно создать новую папку в любом месте, потому что мы ее дальше будем вмонтировать и далее в docker-compose например, ставим новый `environment` - `LANGFLOW_LOAD_FLOWS_PATH=/app/flows` и далее монтируем нашу папку, пример кода:

 Пример кода для импорта данных.
```Docker-Compose.yml
environment:  
  - LANGFLOW_BACKEND_ONLY=true  
volumes:  
  - ./flows:/app/flows
```

Тут будет так же как с импортом нод, импорт происходит только при запуске LF, во время работы он не будет подтягивать новые пайплайны.

###### ВАЖНЫЙ 
момент, при таком способе нельзя импортировать пайплайны в папках, то есть все файлы должны быть в одной главной папке, а так же нельзя при таком способе нельзя выбирать в каких папка (в LF это Projects) они буду храниться в главной папке (Starter Project), которую нельзя вообще удалить легальными путями.

##### 2.2. Импорт через api.
У LF есть api для импорта пайплайнов, `POST api/v1/flows/upload`, там нужно отправить наш `.json` файл, а так же в query параметрах можно указать в какую папку его импортировать, а так же нужен api ключ для импорта, пример ручки из `/docs` представлен на рисунке 9.

![[Снимок экрана 2025-11-19 в 21.07.12.png]]

## САМЫЕ ВАЖНЫЕ МОМЕНТЫ ПРИ ИМПОРТЕ

- Если мы импортируем пайплайны первым способом, то id пайплайна, по которому мы будем опращаться, сохраняется на другом сервере, то есть будет абсолютно такой же, а при втором варианте, будет создавать каждый раз новый, но в ответе после импорта его можно будет получить по полю `id`.
- У нод существуют разные входные поля, например `StrInput`, `MessageInput` и т.д. но нужно пыть аккуратным с `SecretStrInput`, оно скрывает содержимое данных в UI, но если мы вставим данные в такое поле, неважно как, напечатать просто или использовать глобальные переменные, то при импорте данного пайплайна ДАЖЕ на этот же сервер повторно, то данные слетают, а если еще импортировать это чисто на бек, но чтобы вставить эти данные, придется очень сильно заморочиться, поэтому не рекомендую ставить это поле в ноды.
- При первом варианте нельзя создавать в папке другие папки, поэтому все будет в куче.
- При втором варианте, если импортировать пайплайн с таким же названием, то он получит название с припиской (1)
